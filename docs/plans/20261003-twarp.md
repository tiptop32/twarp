# twarp: раздельная маршрутизация corp / RU direct / VPN поверх sing-box

## Overview

`twarp` — Go CLI, который управляет внешним sing-box (бинарь из brew, root-демон под launchd) и делит трафик macOS на три потока:

1. **corp**: корп-домены и корп-подсети → SOCKS5 `192.168.0.105:8080` (cisco-socks-server в UTM-VM);
2. **direct**: `.ru` / `.su` / `.рф`, `geoip-ru`, `geosite-category-ru`, LAN → напрямую;
3. **vpn**: всё остальное → личный VPN (VLESS + Reality).

Заменяет связку Outline (default route) и старого warp (`~/warp`, Go-форк с TUI). sing-box мы не переписываем: twarp генерирует его `config.json` и rule-set'ы, ведёт список корп-IP и даёт агентам MCP-инструменты, чтобы добавить адрес новой VM в корп-сеть на лету.

**Измеримый результат:**
- один TUN вместо двух, которые дерутся за маршруты; `scripts/smoke.sh` зелёный: корп-хост идёт через `corp`, `ifconfig.me` показывает IP VPN, `2ip.ru` показывает домашний IP, DNS не утекает;
- добавление корп-IP агентом занимает один вызов MCP без sudo и без рестарта TUN; трафик переключается за 3 секунды или быстрее (интеграционный тест);
- агент физически не может увести в корп-прокси адреса вне `corp.allowed_ranges` (unit-тесты + негативные eval-кейсы);
- каждое изменение корп-списка оставляет строку в `audit.jsonl`.

## Testing Strategy

- **gate tests** (`make test` = `go test ./...`): без root и сети, меньше 2 секунд, детерминированные. `render`-тесты требуют `sing-box` в PATH и **падают** с понятной ошибкой, если его нет, а не пропускаются.
- **secret gate** (`make secrets-check`, pre-commit): `gitleaks detect` по репо, ноль находок, без исключений.
- **integration** (`make integration` = `go test -tags integration ./...`): настоящий sing-box без root, с `mixed`/`direct` inbound вместо TUN. Проверки идут по тегу outbound в Clash `/connections`, а не по доступности сети. Тестовые `.srs` компилируются при запуске теста через `sing-box rule-set compile`, бинарные фикстуры в git не коммитятся.
  - Ограничение: при mixed inbound и домене назначения IP-правила (corp-ip, private, geoip) не срабатывают, потому что IP ещё не известен. Поэтому IP-маршрутизация проверяется соединениями на IP, а доменная проверяется отдельно.
- **eval** (`make eval`): 13 кейсов (10 позитивных + 3 негативных) через локальный `claude -p` с подключённым `twarp mcp`, порог 12/13, все негативные обязательны.
- **smoke** (`scripts/smoke.sh`): на живой машине после `install`.
- e2e UI-тестов нет, UI отсутствует.

## Solution Overview

```
~/.config/twarp/twarp.yaml       ┐                          (root, 0600)
~/.config/twarp/secrets.yaml     ├─ sudo twarp apply ─→ /usr/local/etc/twarp/config.json ─→ sing-box (launchd, root)
~/.config/twarp/corp-ips.json    ┘                      /usr/local/etc/twarp/rules/corp-ip.json  (user-owned, hot reload)
        ▲                                                /usr/local/etc/twarp/geo/*.srs          (root-owned)
        │
 twarp corp-ip add / MCP corp_ip_add  (без root: пишет state и rules/corp-ip.json, sing-box перечитывает сам)
 twarp render                         (без root: dry run в stdout или --out DIR)
```

Ключевые решения:
- **sing-box внешний бинарь**, не библиотека: обновление ядра через brew, без GPL-линковки, без build tags.
- **Свои минимальные структуры конфига**, не `github.com/sagernet/sing-box/option`: меньше зависимостей, нет рассинхрона версии модуля и бинаря. Схему страхуют golden-тесты и `sing-box check` установленным бинарём.
- **Горячее обновление через local rule-set**: sing-box следит за файлом (kqueue на darwin) и перечитывает его без рестарта TUN. Полный reload через `launchctl kill SIGHUP` нужен только для `apply`.
- **Права:**
  - только `rules/` принадлежит пользователю, поэтому MCP пишет `corp-ip.json` без sudo;
  - `geo/` и `config.json` принадлежат root; geo обновляет `sudo twarp geo update` или `apply`;
  - под root twarp ничего не пишет в `~/.config/twarp`.
- **Ограничение для агента:** `corp.allowed_ranges` задаёт только пользователь в `twarp.yaml`. MCP и CLI без `--force` принимают только префиксы внутри этих диапазонов.
- **Модель угроз (принятый риск для однопользовательской машины):** root-демон читает `rules/corp-ip.json` из каталога пользователя и запускает бинарь из `/opt/homebrew`, куда пишет пользователь. Любой процесс пользователя может записать в `corp-ip.json` мимо валидации. Geo-файлы вынесены в root-каталог, чтобы подмена `geoip-ru.srs` на `0.0.0.0/0` не могла отправить весь трафик в обход VPN. Риск описывается в README.

## Technical Details

### Пути, пользователь и root

| Что | По умолчанию | Переменная для тестов |
|---|---|---|
| пользовательский каталог | `~/.config/twarp` | `TWARP_HOME` |
| вывод для sing-box | `/usr/local/etc/twarp` (`config.json`, `rules/`, `geo/`) | `TWARP_OUT` |
| логи sing-box | `/usr/local/var/log/twarp/` | — |
| бинарь sing-box | `/opt/homebrew/opt/sing-box/bin/sing-box` → `/usr/local/opt/sing-box/bin/sing-box` → флаг `--sing-box` | `TWARP_SINGBOX` |

Правила для root:
- под euid 0 домашний каталог определяется по `SUDO_USER` через `os/user.Lookup`; если `SUDO_USER` пуст (`sudo -i`, `su`), twarp падает с понятной ошибкой и не использует `/var/root`;
- под euid 0 twarp **не пишет** в `~/.config/twarp`; `audit.jsonl` от root-команд пишется в `/usr/local/var/log/twarp/audit.jsonl`;
- `corp-ip`, `import`, `mcp` отказываются запускаться под root (`do not run with sudo`);
- `apply`, `install`, `uninstall` требуют root; `geo update` требует root, потому что `geo/` принадлежит root.

### `twarp.yaml`

```yaml
corp:
  socks: 192.168.0.105:8080
  domains: [x5.ru, express.ms, ktalk.ru, ktalk.host, rutube.ru, lemanapro.ru]
  dns: 100.64.70.28
  allowed_ranges: [100.64.0.0/10]   # правит только пользователь; RFC1918-подсети корпа добавить сюда вручную
direct:
  dns: 77.88.8.8
  local_domains: [home.arpa]        # резолвятся системным резолвером (type: local)
vpn:
  dns: https://1.1.1.1/dns-query
clash_api: 127.0.0.1:9090
log_level: warn
```
Второй корп-DNS (`192.168.39.45`) не генерируется: в sing-box нет failover между серверами, неиспользуемый сервер был бы мёртвым конфигом. `migrate` пишет его в комментарий как ручной запасной вариант.

### `secrets.yaml` (chmod 600, вне git)

```yaml
vpn_uri: vless://…
clash_secret: <случайные 32 байта hex, генерируются при import>
```

### `corp-ips.json`

```json
{"version": 1, "cidrs": [
  {"cidr": "100.66.84.182/32", "comment": "migrated from warp", "added_by": "migrate", "added_at": "2026-10-03T17:40:00Z"}
]}
```

### Валидация CIDR (`internal/state`)

- `netip.ParsePrefix`, голый IP через `netip.ParseAddr` → `/32` или `/128`; сначала `Addr.Unmap()`, 4in6 превращается в v4 и проверяется по v4-правилам;
- биты хоста обнуляются через `Prefix.Masked()`, в ответ добавляется warning (`100.66.65.149/24` → `100.66.65.0/24`);
- **главное правило:** префикс должен целиком лежать внутри одного из `corp.allowed_ranges`; CLI с `--force` может это обойти, MCP не может никогда;
- дополнительные отказы (независимо от `allowed_ranges` и `--force`): префикс короче `/16` (v4) или `/48` (v6), loopback, unspecified, link-local, multicast, `255.255.255.255`, любой префикс, содержащий адрес корп-SOCKS;
- лимит: 256 записей;
- `remove` нормализует вход так же, как `add` (`100.66.65.149/24` удаляет `100.66.65.0/24`);
- результаты add: `added`, `already_present`, `covered_by <cidr>` (no-op); remove: `removed`, `not_found`.

### Rule-set `corp-ip.json` (source format)

```json
{"version": 2, "rules": [{"ip_cidr": ["100.66.84.182/32", "..."]}]}
```
`version: 2` поддерживается с 1.10, `ip_cidr` более новой версии не требует; фиксируется тестом. Пустой список записывается как `"rules": []`, это допустимая форма для local rule-set (Task 2 подтверждает). Заглушка TEST-NET используется только если Task 2 это опровергнет.

### Inbound TUN

```json
{"type": "tun", "tag": "tun-in",
 "address": ["172.19.0.1/30", "fdfe:dcba:9876::1/126"],
 "auto_route": true}
```
- `dns_mode` остаётся по умолчанию (`hijack`: на Apple ставится per-interface DNS); `dns_address` по умолчанию следующий адрес после первого IPv4, поэтому нужен `/30`;
- `strict_route` не используется: на macOS он ни на что не влияет;
- v6-маршрут остаётся, чтобы v6 не утекал через провайдера, а `dns.strategy: prefer_ipv4` защищает от зависаний на happy-eyeballs, если у VPN нет v6.

### Route-правила (порядок важен)

```
0. action: sniff
1. protocol: dns                                  → action: hijack-dns
2. ip_cidr: [<corp socks ip>/32]                  → direct     защита на всякий случай: LAN в TUN не попадает
3. domain_suffix: corp.domains                    → corp
4. rule_set: corp-ip                              → corp
5. ip_is_private / domain_suffix: local_domains   → direct
6. domain_suffix: [ru, su, xn--p1ai]              → direct
7. rule_set: [geoip-ru, geosite-category-ru]      → direct
final                                             → vpn
```
`route.auto_detect_interface: true`, `route.default_domain_resolver: "direct"` (обязателен в 1.14 при нескольких DNS-серверах). Clash API на `127.0.0.1:9090` с секретом. **`cache_file` не используется**: потребителей у него нет, а под launchd без рабочего каталога он ломает запуск.

Ограничение (идёт в README): несниффаемые протоколы (SSH, RDP) к корп-именам, которые резолвятся в адреса вне корп-списка, маршрутизируются только по IP. Такие адреса нужно добавить в корп-список. `reverse_mapping` на macOS ненадёжен из-за системного DNS-кэша, поэтому на него не полагаемся.

### DNS

```
servers:
  corp:   type tcp,   server 100.64.70.28, detour corp
  direct: type udp,   server 77.88.8.8                 (без detour: "detour: direct" — ошибка с 1.12)
  local:  type local
  remote: type https, server 1.1.1.1, detour vpn
rules:
  domain_suffix corp.domains             → corp
  domain_suffix direct.local_domains     → local
  domain_suffix [ru, su, xn--p1ai]       → direct
  rule_set geosite-category-ru           → direct
final: remote
strategy: prefer_ipv4
reverse_mapping: true                    (вспомогательно, не основной механизм)
```
`vpn` outbound получает `domain_resolver: direct`, чтобы адрес VPN-сервера не резолвился через сам VPN.

### VLESS → outbound

```json
{"type": "vless", "tag": "vpn", "server": "<host>", "server_port": 443,
 "uuid": "<uuid>", "flow": "xtls-rprx-vision",
 "tls": {"enabled": true, "server_name": "<sni>",
         "utls": {"enabled": true, "fingerprint": "edge"},
         "reality": {"enabled": true, "public_key": "<pbk>", "short_id": "<sid>"}},
 "domain_resolver": "direct"}
```
Поддерживается только `vless://` с `security=reality` и `type=tcp`. Остальные схемы (`ss://`, `vmess://`), `security` и транспорты отклоняются с явной ошибкой. Добавим, когда понадобятся.

### MCP (`github.com/modelcontextprotocol/go-sdk`, stdio)

| tool | вход | выход |
|---|---|---|
| `corp_ip_add` | `cidr`, `comment` | `status`, `cidr`, `warnings[]`, `singbox_running`, `note: "written; sing-box reloads within ~1s"` |
| `corp_ip_remove` | `cidr` | `status`, `singbox_running`, `note` |
| `corp_ip_list` | — | `cidrs[]` с комментариями, `allowed_ranges[]` |

`allowed_ranges` через MCP только читаются. Регистрация: `claude mcp add twarp -- twarp mcp`.

### Цепочка мутации (CLI и MCP, всегда под пользователем)

1. `syscall.Flock(LOCK_EX)` на `~/.config/twarp/corp-ips.lock`;
2. чтение state; если файл битый, отказ без перезаписи и путь к файлу в ошибке;
3. валидация и изменение;
4. state → tmp + `rename` в том же каталоге;
5. `rules/corp-ip.json` → tmp + `rename` в том же каталоге (никогда не запись на месте: sing-box может прочитать половину файла);
6. строка в `audit.jsonl`: `{ts, actor (cli|mcp), op, input, result}`;
7. внедрённая `func() bool` (реализация в Task 10: Clash `/version`) говорит, жив ли sing-box; если нет, добавляется warning.

`apply` под root берёт тот же `corp-ips.lock` (только чтение state) перед записью `rules/corp-ip.json`. Записанный файл отдаётся пользователю через chown на `SUDO_UID:SUDO_GID`.

Watcher local rule-set в sing-box ошибки перезагрузки только логирует, поэтому MCP сообщает «записано», а не «применено». Валидность файла гарантируют тесты через `sing-box rule-set compile`.

### Последовательность `sudo twarp install`

1. проверка root, `SUDO_USER`, наличие `twarp.yaml` и `secrets.yaml`;
2. поиск бинаря sing-box (см. таблицу путей); версия ≥ 1.14, иначе ошибка;
3. проверка конфликтов: `route -n get 1.1.1.1` → интерфейс; если это `utunN` и его адрес (`ifconfig utunN`) не `172.19.0.1`, отказ с подсказкой (Outline / warp); если загружен `homebrew.mxcl.sing-box` (`brew services`), отказ;
4. создание `/usr/local/etc/twarp/{rules,geo}`, `/usr/local/var/log/twarp`; `rules/` → chown `SUDO_UID:SUDO_GID`;
5. `geo update` (если файлов нет);
6. render → `config.json` (`0600 root:wheel`) + `rules/corp-ip.json` → `sing-box check`;
7. plist демона → `launchctl bootstrap system /Library/LaunchDaemons/dev.twarp.singbox.plist`;
8. plist geo-агента → `~/Library/LaunchAgents/dev.twarp.geo.plist` (chown на пользователя, абсолютный путь из `os.Executable()`) → `launchctl bootstrap gui/<SUDO_UID>`;
9. `/etc/newsyslog.d/twarp.conf` для ротации логов.

`uninstall`: `bootout` обоих сервисов, удаление plist и newsyslog-конфига. `/usr/local/etc/twarp` и `~/.config/twarp` остаются.

*Items requiring manual intervention or external systems - no checkboxes, informational only*

**Установка на живую машину:**
- остановить Outline (выйти из приложения) и warp (`sudo pkill warp`), проверить `route -n get 1.1.1.1`;
- `twarp migrate`, проверить `allowed_ranges` (добавить RFC1918-подсети корпа, если они есть), `twarp import < key.txt`, `sudo twarp install`;
- `scripts/smoke.sh`, затем `sudo scripts/smoke.sh --leak-check`;
- откат: `sudo twarp uninstall`, запустить Outline и `~/warp/warp-up.sh`.

**Проверить вручную:**
- режим сети UTM: Bridged (VM в LAN `192.168.0.x`, ожидается) или Shared. В Shared трафик AnyConnect из VM пойдёт через TUN хоста и будет маршрутизироваться по geoip, это нужно учесть;
- корп-DNS `100.64.70.28` отвечает по TCP через SOCKS; какие адреса он возвращает для корп-хостов (если RFC1918, добавить их подсети в `allowed_ranges` и корп-список).

**Безопасность:**
- тестовый VLESS-ключ был вставлен в чат; боевой ключ передавать только через `twarp import` из файла или stdin;
- если ключ из чата используется в реальности, ротировать его на сервере.
