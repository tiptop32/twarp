# Несколько VPN с отдельным маршрутом для Google AI

## Overview

Цель: сохранить нынешний VPN основным и добавить второе VLESS REALITY-подключение в тот же sing-box. Один системный TUN, несколько независимых исходящих подключений.

Критерии приёмки:
- Brave и его helper-процессы используют второй VPN для публичного трафика, включая YouTube. Пользователь явно выбрал приоритет приложения над сервисом.
- CLI `agy` использует второй VPN. Выбор пути проверяется по установленному исполняемому файлу.
- Gemini, AI Studio, Antigravity и их выделенные AI API используют второй VPN и в других приложениях.
- YouTube вне Brave и остальной трафик без новых правил сохраняют прежние маршруты. Общие Google IP-префиксы не переносятся на второй VPN.
- Gateway, LAN, локальные домены, основной VPN-only прокси и ограничения MCP сохраняются.
- Недоступность второго VPN не отправляет выбранный трафик напрямую или через первый VPN.
- CLI render, статус и TUI различают подключения; секреты не попадают в вывод, git или eval-артефакты.
- Старый конфиг без дополнительных туннелей даёт прежний результат без обязательной миграции.

Вне задачи: отдельные системные TUN, WireGuard/OpenVPN, балансировка, резервирование, цепочки VPN, импорт всех правил Xray, изменение полномочий MCP.

## Context

- Go CLI. `internal/config/config.go` загружает один `vpn` и `vpn_uri`; `internal/uri/uri.go` уже поддерживает VLESS REALITY.
- `internal/render/render.go` создаёт `gateway`, `direct`, `vpn`, маршруты и DNS. `internal/app/routes.go` использует те же маршруты для представления в TUI.
- `cmd/twarp/cmd_import.go` читает URI исключительно из stdin; `cmd/twarp/cmd_render.go` рекурсивно маскирует секреты.
- Статус проверяет внешний IP основного VPN. Это не проверка работоспособности каждого дополнительного подключения.
- `internal/itest` запускает настоящий sing-box с синтетическими локальными SOCKS/DNS-серверами. `evals` содержит исполняемые сценарии качества.
- На машине установлен sing-box 1.14.2. Проверка синтетического конфига с двумя исходящими подключениями и отдельными DNS-detour завершилась с кодом 0.
- В рабочем дереве уже есть пользовательские изменения, включая `vpn_proxy_port`. Сохранять их; коммитить только строки этой задачи через selective commit.
- LSP недоступен: `gopls` не найден. Перед изменением контрактов повторить проверку доступности; если сервера по-прежнему нет, явно проверить текстовые потребители.

## Development Approach

Расширить существующий конфиг, не заменять весь формат. Основное подключение `vpn` остаётся самостоятельной частью модели; дополнительные туннели имеют имена и отдельные секреты. Это не временный адаптер старого формата.

Работать последовательно в текущем checkout. Общие контракты config/render принадлежат одному исполнителю. Не запускать проверки посреди незавершённых правок; выполнять указанные проверки после законченного блока и итоговый gate один раз. Независимый read-only reviewer получает только код, план и синтетические материалы, без локальных конфигов и присланных ключей.

## Solution Overview

Добавить упорядоченный список `vpn.tunnels`. Каждый элемент: `name`, `dns`, `domains`, `cidrs`, `process_path_regex`. Имя формирует outbound `vpn-<name>` и DNS `vpn-<name>-dns`. Секреты дополнительных подключений находятся в `secrets.yaml` в `vpn_uris`, индексированных по имени. Основные `vpn_uri`, `vpn.dns`, `vpn.cidrs`, `vpn.process_path_regex` сохраняют прежнее назначение.

Для публичного трафика правила процессов имеют приоритет над доменными и CIDR-правилами. Порядок YAML разрешает пересечения внутри одного уровня: сначала все процессы в порядке списка, затем все домены/CIDR в порядке списка. DNS использует те же уровни; без атрибуции процесса остаётся доменное правило. Пустые наборы условий не создают catch-all. Туннель без условий отклоняется как ошибка настройки.

Команда импорта принимает необязательный `--name`: без него обновляет основной VPN, с ним сохраняет отдельное подключение. URI по-прежнему поступает только через stdin. Новый импорт сохраняет прочие VPN, Clash secret и gateway credentials. Общую операцию хранения разместить в `internal/app`, frontend оставить тонким.

Не использовать selector/urltest: здесь требуется одновременная маршрутизация, а не выбор одного активного сервера. Не запускать второй sing-box: конкурирующие системные маршруты не нужны.

## Technical Details

### Контракт конфигурации

Список дополнительных туннелей сохраняет порядок YAML. Имена непустые, ограничены ASCII-буквами, цифрами и дефисом; дубликаты отклоняются. Все сгенерированные теги отделены от встроенных тегов. DNS по умолчанию наследует адрес основного VPN, но запросы идут через собственный detour, не через основной туннель.

Домены нормализуются тем же IDNA-кодом, что gateway/direct. CIDR нормализуются и не допускают default route. Регулярные выражения проверяются при загрузке. Неизвестные YAML-поля по-прежнему отклоняются. Ошибка отсутствующего или некорректного секрета называет туннель, но не включает URI или ключи. Сохранение секретов атомарное, права 0600.

### Приоритет маршрутов

Сохранить начало существующей цепочки: выделенный основной VPN-only listener, sniff, hijack-dns, прямой адрес gateway SOCKS, домены/CIDR gateway, private IP. При наличии дополнительных туннелей затем поставить `direct.local_domains`, включая имена, резолвящиеся в публичные IP. После исключений идут все правила процессов дополнительных VPN, затем их домены/CIDR. Далее сохранить существующие provider/CIDR/process/geo-правила и final `vpn`; позднее правило local в этом режиме не дублировать. Без дополнительных туннелей порядок и golden остаются прежними.

Так Brave побеждает сервисные правила для публичного трафика, а gateway и локальная сеть сохраняют свои исключения. Локальный основной VPN-only прокси остаётся закреплён за первым VPN. Если приложение явно использует этот прокси, правило процесса не может изменить его назначение; проверить настройки целевых приложений до активации.

### DNS

Для каждого дополнительного VPN создать HTTPS-DNS с собственным detour. Сохранить `dns.strategy: prefer_ipv4`, bootstrap через `direct` и `route.default_domain_resolver`. Не допускать резолва адреса VPN через него самого.

Gateway DNS имеет приоритет. При дополнительных туннелях DNS для `direct.local_domains` направляется в `local` раньше любых новых правил процессов/доменов, даже для Brave. Далее идут все новые правила процессов, затем доменов, затем прежние provider/direct-правила; позднее local-правило в этом режиме не дублировать. Порядок YAML действует внутри каждого уровня. CIDR не переносить механически в DNS: IP назначения ещё неизвестен до ответа. Для IP-only маршрутов DNS остаётся по обычным правилам.

На macOS системный DNS может выполняться от имени системного резолвера. В этом случае правило процесса не доказывает изоляцию DNS приложения: применяются доменные правила. Не обещать глобальный kill switch при остановленном TUN или защиту от трафика вне него. Для захваченного TUN-трафика и DNS, выбранного новым правилом, не создавать fallback на direct/основной VPN.

### Google AI и YouTube

Список второго VPN строится из выделенных доменов Gemini/AI Studio/Antigravity и API, подтверждённых документацией и наблюдаемыми соединениями. Не добавлять `google.com`, `googleapis.com` или общие Google IP-подсети целиком: это затронет YouTube и другие сервисы.

Общие ресурсы Google могут обслуживать несколько продуктов по одному хосту. Правила доменов не различают URL-пути внутри HTTPS. Сохранить это ограничение в документации. Весь Brave покрывает такие ресурсы правилом процесса. Для других приложений проверять основной AI endpoint, а не утверждать изоляцию каждого встроенного ресурса. Если AI-хост также обслуживает наблюдаемый YouTube-трафик, не добавлять его автоматически: остановить настройку этого правила и согласовать исключение с пользователем. Приёмка YouTube требует новых соединений страницы и воспроизведения видео, а не только загрузки HTML.

### Диагностика и безопасность

Добавить в app-модель список туннелей: имя, outbound tag, протокол, импортирован/ошибка. Не называть валидный URI доказательством доступности. TUI показывает отдельные строки маршрутов и счётчики соединений каждого outbound; экран правил совпадает с renderer.

`status --net` явно описывает проверку основного VPN. Не сравнивать IP второго VPN с адресом первого. Проверку фактического маршрута делать по Clash chains и запросам к локальным приёмникам в integration.

Присланный пользователем Xray-конфиг используется только для локального преобразования параметров VLESS. Его UUID, ключи, short ID и адрес подключения не записывать в план, тесты, README, команды argv или ревью. Не менять пользовательские `.ru`, gateway и другие правила на правила из вложения.

## Testing Strategy

- Config: прежний формат, несколько туннелей, нормализация, дубликаты, неизвестные поля, пустые условия, плохие CIDR/regex/DNS, round-trip секретов и права.
- Render: независимые outbound/DNS-detour, отсутствие catch-all, приоритет gateway/private/process/domain, старый golden без изменений, ошибки без секретов.
- Import: именованный импорт через stdin, повторный импорт одного имени не затрагивает другие секреты, запрет URI в argv/root, маскирование всех подключений.
- App/TUI: разные теги и счётчики, неизвестный/неимпортированный туннель не выглядит подключённым, правила отражают действительный порядок.
- Integration: настоящий sing-box, два независимых локальных SOCKS-сервера, одновременные соединения, DNS через выбранный detour, отказ второго сервера без обращения к первому/direct. Домены и процессы проверяются как конкурирующие условия.
- Eval: отдельный runner с pass threshold 100%; явный отказ при отсутствующих сценариях. Подключить к `make eval` и shell lint.
- После законченных блоков: `go test ./internal/config ./internal/render ./internal/app ./cmd/twarp`.
- Итог: `make test lint secrets-check integration eval`.
- До поставки: независимое ревью, затем оценка результата; только после этого selective commit и обычный push.
